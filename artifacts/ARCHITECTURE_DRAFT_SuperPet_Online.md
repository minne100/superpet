### 1.2 设计原则

| 原则 | 说明 |
|---|---|
| **去中心化对等** | 所有节点独立运行完整 game-engine，无人为主机 |
| **全知但隔离** | 系统全知所有状态，UI 层根据玩家权限控制显示 |
| **最少广播** | 只广播操作事件，不广播计算结果。各节点独立运算 |
| **100% 拟真** | 渲染层模拟实体桌游体验，无 HUD 光效/气泡 |
| **零服务器成本** | 信令服务器无状态，游戏开始后无负载 |

### 2.1 连接拓扑

```
        ┌─────────────┐         ┌─────────────┐
        │  玩家 A      │◄───────►│  玩家 B      │
        │  (浏览器)    │         │  (浏览器)    │
        └──────┬──────┘         └──────┬──────┘
               │◄─────────────────────►│
        ┌──────┴──────┐         ┌──────┴──────┐
        │  玩家 C      │◄───────►│  玩家 D      │
        │  (浏览器)    │         │  (浏览器)    │
        └─────────────┘         └─────────────┘

        ┌──────────────────────────────────────┐
        │         Rust 信令服务器                │
        │  (仅开局时参与，之后所有通信走 WebRTC)   │
```

- 每对节点之间建立一条 WebRTC DataChannel
- 每节点 = N-1 条通道（3或1或2）
- 消息从 DataChannel 直接送达目标节点，无需服务器中转

### 2.3 同步矩阵（完整版）

| 游戏操作 | 广播内容 | 谁算结果 | 需要核验？ |
|---|---|---|---|
| **投骰子** | 骰子轨迹帧 + 最终点数 | 广播方算出点数同时广播 | ❌ 直接使用广播值 |
| **跑圈移动** | 步数（来自骰子结果） | 各节点独立 | ✅ 必然一致 |
| **修炼加属性** | 使用的内功卡编号 | 各节点独立 | ✅ 必然一致 |
| **抽卡** | 卡牌编号（由牌堆种子决定） | 各节点独立 | ✅ 种子相同结果一致 |
| **机遇/事件卡** | 卡牌编号 + 选择详情 | 各节点独立 | ✅ |
| **比武初始落位** | 坐标 + 方向 | 直接广播 | ❌ 系统记录即可 |
| **比武出招** | 招式编号 | 各节点独立算命中 | ✅ 系统全知坐标，结果一致 |
| **比武移动** | 新坐标 + 方向 | 直接广播 | ❌ 系统记录 |
| **战斗结算** | 无需广播 | 各节点独立 | ✅ |
| **购买商店卡** | 购买的卡牌编号 | 直接广播 | ❌ |

**关键原则：** 只有涉及"选择"和"私人信息交换"的才需要额外广播层。纯数值和已知信息的各节点自己算。

### 2.4 卡牌多轮广播场景

#### 事件#3 示例：最大骰子夺最小骰子招式卡

```
1. 触发者广播: card_triggered { cardId: 'event_003' }
2. 所有玩家: 广播各自的骰子数 dice_result { value: <number> }
3. 各节点: 算得A最大、D最小
4. 系统向A展示D的手牌列表（A作为最大骰子获得者，需要主动选择）
5. A 选择一张 → A 广播: card_selection { cardId: 'event_003', chosenCard: 'move_12', from: 'D' }
   原因: A是主动方，A选完直接广播结果。D手牌移除move_12，A手牌增加move_12
```

#### 涉及私人信息交换的场景清单

| 场景 | 需要额外广播 |
|---|---|
| **夺牌类**（事件#3/4、机会#6/7/10/11/20/21/27/28） | 被夺方公开被拿走的卡牌编号 |
| **换牌类**（事件#18/19、机会#20/21） | 双方分别公开拿走的卡牌 |
| **金币买卖卡**（事件#20/21） | 交易的卡牌编号 |
| **修炼用内功卡** | 使用哪张内功卡（攻/防选择） |
| **选择弃卡**（机会#6/7） | 弃了哪张 |

### 3.2 确定性洗牌算法

```javascript
// 使用 Fisher-Yates + 种子化 PRNG
// 保证同一种子下所有节点牌堆顺序一致

class SeededRNG {
  constructor(seed) {
    this.state = seed;
  }
  
  // xoshiro128** 算法（简单、质量高、跨语言一致）
  next() { /* ... */ }
  
  // 返回 [0, max) 的整数
  nextInt(max) { return Math.floor(this.next() * max); }
}

function shuffle(array, rng) {
  const result = [...array];
  for (let i = result.length - 1; i > 0; i--) {
    const j = rng.nextInt(i + 1);
    [result[i], result[j]] = [result[j], result[i]];
  }
  return result;
}
```

**种子生成规则：** 房主在游戏开始时生成4个独立种子（机遇/事件/招式/内功），通过 `deck_seeds` 消息广播。各节点接收后初始化牌堆。

**卡牌使用后的同步：**
- 牌堆顺序在开局锁定，有人抽走一张卡后，所有节点知道这张卡已不在牌堆
- 手牌变更通过广播通知（抽到/获得/失去卡牌时广播卡牌编号）
- 各节点分别更新自己的本地手牌状态

### 3.4 UI 层屏蔽策略

**屏蔽罩设计方案：用物理模型解决问题**

屏蔽罩是放置在战场上的物理隔离装置——类似实体桌游中那种竖立在桌面的遮挡板。它的作用就是物理上遮挡来自两侧的视线，因此：

1. **不需要逻辑层的屏蔽计算。** 所有节点始终知道所有人的位置（系统全知），UI 层直接根据状态渲染即可。
2. **不需要渲染对手在对战盘上的棋子。** 屏蔽罩物理上挡住了——你的视角看不到对面玩家的棋子。
3. **位置卡效果：** 使用后直接在的棋盘上用不同颜色标记坐标，不渲染棋子模型。

**建模要求：**
- 屏蔽罩外形要充分考虑，不能太厚（否则盒子里放不下），也不能太薄（否则遮不住两侧视线）
- 参考实体桌游中的立式遮挡板设计
- 材质半透明或不透明，确保看不到对面棋子

**系统层：** 所有节点仍然维持全知状态，攻击招式命中判定等照常进行（因为系统知道所有人的位置）

- **旋转（手机）：** 按住画面左右滑动，在一定角度范围内旋转视角
- **禁止：** 自由漫游、穿模

## 5. PHP 信令服务器设计

### 5.1 功能范围（最小化）

```
┌───────────────────────────────┐
│    Rust 信令服务器              │
│                               │
│   /api/room/create  → 创建房间 │
│   /api/room/join    → 加入房间 │
│   /api/room/list    → 房间列表 │
│   /api/stats        → 统计信息 │
│   /ws               → WebSocket│
│      (房间内信令 + ICE交换)    │
└───────────────────────────────┘
```

### 5.2 数据流

```
创建房间：
  1. 客户端 POST /api/room/create
  2. 服务器生成 4位base36 房间码
  3. 返回房间码 + WebSocket 连接地址
  4. 返回进房链接 + 二维码数据

加入房间：
  1. 客户端 POST /api/room/join { roomCode, password? }
  2. 公开房：校验房间码是否存在
  3. 私有房：校验密码
  4. 成功后返回 WebSocket 地址 + 房间内现有玩家列表

ICE 交换（通过 WebSocket）：
  A → 服务器: offer (SDP)
  服务器 → B: offer
  B → 服务器: answer
  服务器 → A: answer
  (ICE candidate 同理)

心跳：
  WebSocket 保持连接，60秒无消息断开
  不影响游戏进行（游戏全走 WebRTC）
```

### 5.3 技术选型

| 组件 | 选择 | 理由 |
|---|---|---|
| HTTP | 静态HTML + js调用API显示统计数据 | 可部署在任何地方 |
| API 框架 | infinityfree PHP | 永久免费 |
| WebSocket | PHP workerman | 永久免费 |
| 房间存储 | HashMap in-memory | 无状态，崩溃后房间丢失可接受 |
| 部署 | 直接文件复制 | 无需编译 |

## 6. 断线 & AI 托管

### 6.1 断线检测流程

```
每 5 秒：每个节点广播 ping
15 秒未收到某节点 ping：
  → 触发 disconnection 流程

断线流程：
  1. 任意在线节点检测到超时 → 广播 player_disconnected
  2. 所有节点同意断线 → 开始 30 秒计时
  3. 如果断线节点在 30 秒内重连（通过信令服务器）：
     a) 请求 state_sync
     b) 任意在线节点回复完整 GameState
     c) 重连节点恢复，继续游戏
  4. 如果 30 秒超时：
     a) 广播 player_kicked
     b) 该节点从房间中移除
     c) AI 托管接管
```

### 6.2 AI 托管策略

```javascript
class AITurnManager {
  takeTurn(playerState, gameState) {
    // 跑圈阶段
    if (gameState.phase === 'track') {
      return {
        action: 'roll_dice',  // 自动物理摇盅（物理引擎模拟）
        // 自动前进（由 game-engine 处理）
        // 自动修炼，但不使用内功卡
        // 自动抽机遇/事件卡并执行
      };
    }
    
    // 比武阶段
    if (gameState.phase === 'battle') {
      const myPos = playerState.battle.hexPos;
      const center = [0, 0, 0];
      
      return {
        action: 'attack',
        moveCard: randomChoice(playerState.battle.wushuDeck),
        // 出招后向中心移动一格
        moveDirection: directionTowards(center, myPos),
        // 可使用手上已有的比武卡（闪避/反弹）
        // 但不主动购买商店卡
      };
    }
  }
}
```

## 9. 关键架构决策记录

| ID | 决策 | 理由 | 替代方案 |
|---|---|---|---|
| ADR-001 | 去中心化全节点运算 | 零服务器成本，防作弊 | 主从架构（被否决） |
| ADR-002 | 最少广播原则 | 减少网络依赖，中国NAT环境友好 | 全状态广播（被否决） |
| ADR-003 | 确定性牌堆种子 | 保证一致性，无需同步牌堆 | 实时同步洗牌（浪费时间） |
| ADR-004 | 物理动画作为UI层，结果作为数据层 | 避免物理引擎不一致 | 全物理模拟同步（被否决） |
| ADR-005 | Rust 信令服务器 | 小内存、高并发、单二进制部署 | Node.js（太重） |
| ADR-006 | game-engine.js 纯JS（非TS） | 与模拟器零成本复用 | TS（需要编译步骤） |
| ADR-007 | 不做TURN服务器 | MVP阶段省成本 | 备选：TURN（后继） |
| ADR-008 | 无2D降级 | 维护100%拟真体验一致性 | 2D模式（被否决） |

## 11. 卡牌引擎

详见独立文档：`/home/lu/superpet/artifacts/card_engine_design_event3.md`

### 11.1 核心思路
- 所有卡牌规则用 **JSON 描述**，引擎解析执行，新增/修改无需改代码
- 每步执行分 **role**（actor/target/others/all），各节点各演各的
- 网络广播仅传 **cardId + 编号**，不传文字内容
- 所有卡牌 Json 文件集中存放在 `/home/lu/superpet/cards/` 目录下

### 11.2 本地化（Localization）
PRD v1.3 要求支持多语言。策略：
- **卡牌 Json 不包含任何显示文本**（`notify_all` 只传 cardId，不传 message）
- UI 层根据 cardId + stepId 查本地化表（`/locales/zh-CN.json`, `/locales/en-US.json` 等）
- 示例本地化条目：
  ```json
  {
    "card.event_003.title": "掠夺",
    "card.event_003.step.notify": "事件#3：掠夺！所有玩家请投骰",
    "card.event_003.step.winner_select": "{actor} 正在从 {target} 的手牌中选择",
    "card.event_003.step.end": "事件#3结束：{winner} 从 {loser} 处夺取了 {card}"
  }
  ```
- 默认中文，启动时根据浏览器语言偏好或用户设置切换
- 引擎保持语言无关性，只负责执行逻辑+暴露 cardId/stepId/变量值给 UI 层渲染
